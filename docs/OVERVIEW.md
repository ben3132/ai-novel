## 0. 一句话

**这套工具回答一个问题：AI 写到第 300 章时，还记得第 30 章定下的设定吗？**

长篇连载小说的真正难点不是"写不出字"，而是 **一致性**：

- 三章前刚给配角起了名字，这一章又换了个新的
- 主角的能力上限在第 50 章改过，第 200 章却按旧版打
- 世界观设定散在 89 个文档里，写到哪查到哪，查不完全
- 引用了原作角色，但记不清原作里他到底是什么性格

靠人记不可行，靠单次对话上下文更不可行（窗口装不下）。所以需要**外部化的记忆**——
这就是这套工具的全部理由。

## 1. 三个项目各管什么

```
                    你的小说
                       │
        ┌──────────────┼──────────────┐
        │              │              │
   ① 查原作资料    ② 记住自己      ③ 审自己
        │              │              │
        ▼              ▼              ▼
   ┌─────────┐   ┌───────────┐  ┌───────────┐
   │   xs    │   │   两库    │  │   ce      │
   │ L1 知识 │   │  L2 事实  │  │  L3 判据  │
   └─────────┘   └───────────┘  └───────────┘
```

| 项目 | 层 | 一句话 | 没有它会怎样 |
|---|---|---|---|
| **xs** | L1 外部知识 | 把原作拆成可溯源的证据库 | 跨世界观同人里，「哪些名字是原作的」只能靠记忆 |
| **novel-asset-hub** | L2 应然 | 作者裁定的设定真相，写成卡片 | 每次设计情节都造新角色、忘掉旧设定 |
| **novel-memory-system** | L2 实然 | 从已写正文自动提取事实 | 「正文里到底写没写过」只能靠人翻 |
| **novel-creation-engine** | L3 | 按规范审章节，出可回查报告 | 判据全靠人眼，标准随心情漂移 |

> 用户常说的"三个项目"指 **asset-hub / memory-system / creation-engine**（小说创作主线）；
> **xs** 是服务于 IP 研究的配套项目，可选。

## 2. novel-asset-hub —— 设定资产管理（L2 应然）

### 它是什么

一部小说的**设定真相源**。每个设定（人物/势力/能力/道具/地点/剧情线）是一张 Markdown 卡片，
写在 `cards/<类型>/<名字>.md`。

### 解决什么问题

| 问题 | 它的做法 |
|---|---|
| AI 每次设计情节都造新角色 | **写前** `brief` 把相关卡片喂给它 |
| AI 忘记自己定过的设定 | **写后** `check` 全库审计，揪出矛盾 |
| 改了设定，正文没跟上 | 双向校验（见 §5） |
| AI 在正文里现编了个名字 | `orphan` 反向扫描：正文出现但库里没登记 |
| 角色改了名，全库引用断链 | `rename` 自动改文件 + 旧名降级为别名 + 全库替换 |

### 数据长什么样

工作区在你的小说仓库里，**不在工具目录**：

```
<小说仓库>/设定资产/
├── cards/<类型>/<名字>.md   ← 唯一真相源，人/Agent 手写
├── workspace.json            ← 工作区配置（项目名 / 类型集合 / 正文章节目录 / IP 证据库路径）
├── assets.db                 ← SQLite 派生索引，可重建
├── _registry.json            ← 派生缓存，可重建
├── 00_索引.md                ← 派生缓存，可重建
├── _log.md                   ← 变更日志
└── README.md
```

**当前实际规模**（`综漫：\设定资产\`）：

| 类型 | 卡片数 |
|---|---|
| 人物 | 10 |
| 设定 | 6 |
| 道具 | 4 |
| 剧情线 | 2 |
| 势力 | 2 |
| 地点 | 2 |
| 能力 | 1 |
| **合计** | **27 张 / 150 KB** |

### 关键设计

- **卡片是判决，不是摘要**。它记录"这条设定**应该**是什么"，可以和正文不一致——
  不一致本身就是待修的问题。
- **零依赖**。纯 Python 标准库，拷过去就能跑。
- **派生索引可重建**。`assets.db` / `_registry.json` / `00_索引.md` 都能从 `cards/` 重新生成，
  所以只有卡片需要备份。
- **铁律**：改过 `cards/` 必须 `nah sync`；改角色名必须用 `nah rename`。

## 3. novel-memory-system —— 长程记忆库（L2 实然）

### 它是什么

从**已写正文**自动抽取事实，存进 PostgreSQL + pgvector，供检索。

### 解决什么问题

正文写了 20 万字之后，人不可能记得"苏挽第一次出场是在哪一章、当时穿的什么"。
这个项目把正文 ETL 成结构化事实，让这些问题可以**查**。

### 数据长什么样

- **PostgreSQL 16 + pgvector**，通过 `docker-compose.yml` 起容器
- Schema 在 `init.sql`
- 分**长程 / 中程 / 近程**三层记忆
- 数据落 Docker 命名卷 `pgdata`，**不在任何项目目录里**
- 连接串由 `.env` 的 `DATABASE_URL` 决定（该文件不入库）

### 与 asset-hub 的关系（重要）

| | novel-asset-hub | novel-memory-system |
|---|---|---|
| 存的是 | **应然**：作者裁定的设定真相 | **实然**：从已写正文提取的事实 |
| 写入方式 | 人/Agent 手写卡片 | ETL 自动提取 |
| 能否重建 | **不能**（是判决） | **能**（重跑 ETL 即可） |
| 存储 | Markdown 卡片 + SQLite | PostgreSQL + pgvector |
| 回答 | 这条设定**应该**是什么 | 正文里**实际**写了什么 |

**两者都不能当对方的副本。** 它们的**差集**才是最有价值的东西
（见 §5 双向校验）。

### 前置条件

需 PostgreSQL 16 + pgvector 在运行，Python 侧需 `asyncpg` + `pgvector`。
**当前本机未起容器、未装依赖**，所以 `ce doctor` 里它是 `✗`。
不装不影响 asset-hub 和 creation-engine 使用。

## 4. novel-creation-engine —— 判据评审（L3）

### 它是什么

**不是第四个库**，是「**一层适配 + 一套判据**」。

只做三件事：
1. 按正确时序调外部命令
2. 把写作规范变成可执行检查
3. 产出「**依据 → 命中 → 建议**」三段式可回查报告

**边界铁律：已经有项目做的东西，L3 只接线，不重复实现。**
重复实现的风险不是浪费代码，而是**同一份事实出现两个写入者**。

| 能力 | 归属 | L3 怎么做 |
|---|---|---|
| 已写正文的梳理提取 | nms | 子进程调它 |
| 位置/世界观/原作知识归纳 | xs | 子进程调它 |
| 本书设定登记与审计 | nah | 子进程调它 |
| **编排时序 · 判据裁决 · 报告留痕** | **L3** | 本仓库 |
| 编写正文 / 去 AI 味 | L3 只做**接线** | 不自接 LLM，产 Brief 交 Agent |

### 三闸门

| 闸门 | 判据来源 | 数据源 | 性质 |
|---|---|---|---|
| **禁则闸** | 写作规范 §23（八条红线） | 纯本地 | 机械可判 |
| **铁律闸** | 写作规范 §24 / §25 | 纯本地 | 机械可判 |
| **设定闸** | —— | **外部**：nah（应然）+ nms（实然） | L3 只转述，不裁决 |

**外部项目全缺席时 `--no-setting` 仍可跑**，禁则闸 + 铁律闸是纯本地的，零依赖。

### 报告长什么样

每条命中必带四段，缺一不可：

```python
Hit(
    rule_id="§23-6",
    rule_name="禁止结尾喊口号",
    severity="红线",
    line=237,
    snippet="那么，英雄登场",     # 【命中】
    basis="总纲 §23：…",          # 【依据】
    advice="把口号换成…",          # 【建议】
    confidence="mid",             # high / mid / low —— 启发式必诚实标注
)
```

### 一条设计信条：宁可少报，不可误报

节拍闸（§25-1）曾用正则从章末提取"新专名"，结果抽出「**脸兴奋的**」「**跑到街**」这类噪声。
根因：**中文没有词边界**，`[\u4e00-\u9fa5]{2,4}(?=道)` 会把"跑到街**道**"的"跑到街"当说话人。

所以 v3 改成**只给客观量**（字数/段数/对话占比/章末节选）+ 待答问题。
**噪声比不报更糟**——它会淹没真问题、损害整份报告的可信度。

需要实体清单时，L3 明确指向 `nah orphan` / nms 实体提取——**那是它们的职责**。

## 5. xs —— IP 证据采集（L1，可选）

### 它是什么

把原作（动漫/游戏/小说）的文本拆成**可溯源的证据库**，回答
「**这个原作里，某某是什么样、原文怎么写的**」。

### 数据长什么样

每个 IP 一个 `evidence.sqlite3`，位置 `<数据根>/data/ip/<ip>/processed/index/`：

| 表 | 内容 |
|---|---|
| `sources` | 来源登记（含可信等级 trust_level） |
| `text_units` | 文本单元 |
| `context_windows` | 检索窗口（**`orphan` 判定"原作既有角色"就靠它**） |
| `windows_fts` | 全文索引 |

**当前实际数据**（`D:\gz\xm\ai_gq\kf\xs_data\`，共 2 GB）：

| IP | 数据规模 | evidence.sqlite3 |
|---|---|---|
| douluo（斗罗大陆系列） | 2 GB | 1 GB |
| ben10 | 89 MB | 47 MB |
| jackie_chan（成龙历险记） | 52 MB | 29 MB |
| pacific_rim（环太平洋） | 5 MB | 3 MB |
| lol | 2 MB | 无（仅原始素材） |

每 IP 目录结构：

```
data/ip/<ip>/
├── raw/                    原始采集素材
└── processed/
    ├── index/evidence.sqlite3   ← 只读证据库（检索入口）
    ├── units/  windows/         文本单元与检索窗口
    ├── derived_text/            PDF/图片转出的文本
    ├── research/                研究状态
    └── （douluo 另有 entities/ facts/ timeline/ vector/ 等完整处理链）
```

### 可信等级（重要）

| trust_level | 含义 |
|---|---|
| 1 | official_primary —— 官方一手 |
| **11** | **third_party_transcription —— 必须与 L1 原件交叉核验（强制警告）** |
| 2 | cited_fan_reference —— 有引用的粉丝资料 |
| 3 | secondary_community —— 社区二手 |
| 4 | lead_only_excluded —— 仅线索，已排除 |

`answer_status` 恒为 `evidence_only` —— 返回的是**候选证据，不是已确认设定**。

### 与主线的唯一耦合点

`asset-hub` 的 `workspace.json` 里有个 `ip_evidence` 字段，指向若干 `evidence.sqlite3`。
`nah orphan` 用它判定「这个名字是不是原作的」——命中就不必登记进本书资产库。

**没有这个过滤，`orphan` 的输出会被原作角色淹没。**

当前配置指向三个 IP：`jackie_chan` / `ben10` / `pacific_rim`（正好对应主线的三个世界落点）。

## 6. 数据流向

```
原作文本 ──采集──▶ xs 证据库 ──只读──▶ nah orphan 的"原作已知"判定
                       （2 GB）

你的正文 ──┬──────────────────────▶ nah scan / brief  （写前读档）
（89 章     │                         nah check / orphan（写后校验，双向）
 20 万字）  └──ETL──▶ nms 记忆库 ────▶ 语义检索

设定卡片 ──▶ nah add（含三层查重）← 唯一真相源
（27 张）  └─▶ nah sync ─▶ assets.db（派生：变更史 / 影响面 / 改名传播）

     ↓ 写完一章
ce review ─▶ 禁则闸 + 铁律闸（本地）+ 设定闸（调 nah/nms）──▶ 三段式报告
```

### 双向校验：两库合起来才闭环

| 方向 | 谁执行 | 查出什么 |
|---|---|---|
| 应然 → 实然 | `nah check`「已登记但正文未出现」 | 冗余登记 / 别名没挂全 |
| **实然 → 应然** | `nah check` / `nah orphan`「正文出现但未登记」 | ⭐ **AI 现编设定的入口** |
| 库内自洽 | `nms validate_consistency` | 空摘要 / 孤儿事件 / 悬挂引用 / 时间线矛盾 |
