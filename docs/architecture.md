# 架构：AI 小说创作的五个层次

> 本文说明「一套 AI 小说创作管线」由哪些部分组成、各部分的职责边界在哪。
> 它服务于一个目的：**让写出来的内容始终对得上已确立的设定**。

## 0. 为什么需要这份文档

单靠一个工具解决不了「AI 胡编」——因为胡编有两种方向，需要两套机制：

| 方向 | 症状 | 该由谁管 |
|---|---|---|
| 应然 → 实然 | 登记了设定，正文却没写 / 写岔了 | 资产库（`check`） |
| 实然 → 应然 | 正文里冒出新名字，库里没有 | 资产库（`orphan`）+ IP 库 |

再加上「缺知识」和「要生产力」两种诉求，就构成了下面的五层。

## 1. 全景

```
L0 规范层    总纲 V2.0（存储规则 / 写作规则 / 异能设计）        约束以下所有层
              ↓
L1 知识供给  xs IP 采集项目 ──→ IP 证据库（ben10 / jackie_chan / …）  补「原作是啥样」
              ↓
L2 本书事实  novel-asset-hub（应然）  ∥  novel-memory-system（实然）  管「本书是啥样」
              ↓                        ↕ 双向校验
L3 创作层    novel-creation-engine（编排时序 · 判据裁决 · 评审报告）  管「怎么调、怎么裁、怎么留痕」
              ↓
L4 作品本体  小说正文仓库（章节目录 · 参考规范 · 素材）· 由作者自行组织
```

## 2. 各层职责

### L0 规范层 —— 总纲
- 位置：作者小说仓库内的规范文档（如 `<小说仓库>/参考/总纲.md`），由作者自行维护
- 内容：IP 分类判定标准 + 知识库存储体系 + 小说写作规则 + 异能设计方法论
- **它既不是数据也不是工具**，是约束。所有项目的行为都应能追溯到它。
- 注意：它是**文档**，靠人/Agent 遵守，工具不会强制它。

### L1 知识供给 —— xs IP 采集项目
- 位置：工具 `<repo>/xs/`，数据 `<repo>/xs_data/data/ip/<ip>/`
- 产出：每个 IP 一个 `evidence.sqlite3`（`sources` / `text_units` / `context_windows` + FTS）
- 回答的问题：**这个原作里，某某是什么样、原文怎么写的**
- 关键用途（给 L2）：作为**「原作既有角色」的判据**。名字命中 IP 证据库 ⇒ 属原作，不必登记进本书资产库。

### L2 本书事实 —— 两个库，两种性质

| | novel-asset-hub | novel-memory-system |
|---|---|---|
| 存的是 | **应然**：作者裁定的设定真相 | **实然**：从已写正文提取的事实 |
| 写入方式 | 人/Agent 手写卡片 | ETL 自动提取 |
| 能否重建 | 不能（是判决） | 能（重跑 ETL 即可） |
| 存储 | Markdown 卡片 + SQLite 派生索引 | PostgreSQL + pgvector |
| 回答 | 这条设定**应该**是什么 | 正文里**实际**写了什么 |

**边界铁律：两者都不能当对方的副本。**
- 卡片不是「正文的摘要」——它是作者的判决，可以和正文不一致（不一致本身就是待修的问题）；
- 记忆库不是「资产库的另一种存法」——它是可重建的观测结果。

**双向校验（这就是两库合起来才闭环的原因）：**

| 方向 | 谁执行 | 查出什么 |
|---|---|---|
| 应然 → 实然 | `nah check` 的「已登记但正文未出现」 | 冗余登记 / 别名没挂全 |
| 实然 → 应然 | `nah check` / `nah orphan` 的「正文出现但未登记」 | **AI 现编设定的入口** |
| 库内自洽 | `nms validate_consistency` | 空摘要 / 孤儿事件 / 悬挂引用 / 时间线矛盾 |

### L3 创作层 —— `novel-creation-engine`（已落地 v0.1.0）

**定位（2026-09-16 修订）：不建库、不存事实、不做检索。**
它不是第四个库，是**一层适配 + 一套判据**，只做三件事：
① 按正确时序调外部命令　② 把总纲判据变成可执行检查　③ 产出「依据 → 命中 → 建议」三段式可回查报告。

**边界铁律：已经有项目做的东西，L3 只接线，不重复实现。**
重复实现的风险不是浪费代码，而是**同一份事实出现两个写入者**。

- 名义上要干的 **拆书** 已由 nms 的 ETL 承担 → L3 调它，不重做
- **编写** 仍归 L3，但**实现路径是「把 Brief 交给 Agent」，L3 不自接 LLM**
  （依据：xs `get_agent_guidance()` 的 `embedded_llm_required: False`、`decision_owner: connected_agent`）
- **去AI** 归 L3，落地为 `ce review` 的禁则闸 + 铁律闸

已实现：`ce review`（只读三闸门）· `ce doctor` · 33 项离线自测。
代码在 monorepo 的 `novel-creation-engine/` 子目录。
**方案与踩坑记录见 [`creation-layer.md`](creation-layer.md)、`novel-creation-engine/README.md`、`novel-creation-engine/CHANGELOG.md`。**

### L4 作品本体
- 位置：作者自建的小说仓库根目录
- 典型结构：`原著/`（投稿原件，只读）｜`processed/raw/`（工作副本）｜`参考/`（规范与资料包）｜`设定资产/`（= L2 的工作区）

## 3. 「拆书」是两件事，别混

| | 拆别人的书 | 拆自己的书 |
|---|---|---|
| 对象 | IP 原作 / 参考书 | 已写的章节 |
| 谁做 | xs IP 采集项目（L1） | novel-memory-system（L2） |
| 方法 | 文本 → 结构化事实 | 文本 → 结构化事实（同） |
| 目的 | **忠实原文**，建证据 | **服务一致性校验**，建记忆 |
| 质量标准 | 不许走样，要能溯源 | 允许偏差，要能重建 |

方法相同、`质量标准相反`——所以必须分开命名，否则沟通时会互相误导。

## 4. 工具之间怎么接

```
                    ┌──────────────────────────────┐
   总纲 V2.0 ──────▶│  人 / Agent 遵守（无强制）      │
                    └──────────────────────────────┘

   xs 证据库 ──只读──▶ nah orphan 的「原作已知」判定
                     （workspace.json: ip_evidence）

   正文 *.md ───────▶ nah scan / brief   （写前读档）
              ───────▶ nah check / orphan（写后校验，双向）
                     │
   卡片 cards/*.md ──▶ nah add（含查重）  ← 唯一真相源
                  ──▶ nah sync ──▶ assets.db（派生：变更史 / 影响面 / 改名传播）
```

- **配置入口**：工作区 `<工作区>/workspace.json`
  ```json
  {
    "name": "我的小说",
    "types": ["人物", "势力", "能力", "道具", "地点", "设定", "剧情线"],
    "chapters_dir": "../processed/raw",
    "ip_evidence": [".../ip/jackie_chan/processed/index/evidence.sqlite3"]
  }
  ```
- `ip_evidence` 是 L1↔L2 的**唯一耦合点**：只读、可选；不配也能跑，只是 `orphan` 退化为二分类。

## 5. 已知缺口与扩展点

| 缺口 | 影响 | 可能的补法 |
|---|---|---|
| L3 创作层原本无承接者 | 编写与去AI 全靠人 | **已落地** → `novel-creation-engine` v0.1.0（`ce review` / `ce doctor`）。方案见 [`creation-layer.md`](creation-layer.md) |
| `orphan` 是句式启发式 | 召回有限（依赖作者的对话句式），只保证高精度 | 换更强的中文 NER；或写作时约定在正文/大纲保留 `[[双链]]` |
| IP 证据库没有实体名录 | `orphan` 只能靠全文 `LIKE` 命中判定，同名词会误判 | 在 xs 侧产出 entity 词典，或给 IP 库加实体表 |
| 与 nms 尚无自动对接 | 「正文写了但没登记」目前只在本项目内闭环，未与 nms 比对 | 写一个 adapter 读 nms 的 `characters`/`world_settings` 做三方对账（已排入 `creation-layer.md` 的后续阶段） |
| `never_used` 对「元设定」误报 | 约束「怎么写」的卡片（写作口径 / 配置表 / 修订台账）整卡名本就不入正文，会被永久报为「已登记但正文未出现」 | **已修**（2026-09-15）：front matter 打 `tags: [元设定]` 即豁免，改判「其实例是否落地」（见下节） |
| `never_used` 只认整卡名 | 卡片名与正文用词不一致时会漏报（如「超自然复苏」vs 正文「灵气复苏」） | **已修**：别名 `aliases` 参与匹配；整卡名不入正文者改打 `元设定` 标签并在「写作注意」写明正文用词 |

### 5.1 `元设定` 豁免机制（2026-09-15 新增）

**背景**：`check` 的「已登记但正文未出现」原本只看「卡片名/别名是否在正文中出现」。
但资产库里有一类卡片**整卡名天然不入正文**——它们约束的是**怎么写**，不是**世界里有什么**：

| 卡片 | 性质 | 正文里的对应物 |
|---|---|---|
| 三主体架构 / 派遣制 | 叙事分工口径 | 无（不应出现） |
| 世界×英雄配置 | 作者侧配置表 | 各世界的具体形态 |
| 写作节奏·三段循环 | 编辑节奏 | 无（不应出现） |
| 设定修正三规则 | 修订台账 | 无（不应出现） |
| 变身规则 | 正典解释 | 「U 盘」「倒模」（ep_037 / ep_058） |

**机制**：卡片 front matter 打上 `tags: [元设定]` →

1. 该卡**不进** `never_used` 主清单；
2. 改为检查「**其实例是否落地**」——只看卡片 `## 档案` 段里写的实例名（不把 `## 关系` 段的
   卡片间引用当正文实例），若全部落空才报 `meta_never_used`；
3. 输出末尾提示「已豁免 N 项元设定卡片」。

**为什么不能简单删卡**：这些是**作者裁定**（不可重建），删了就丢了判决依据。
豁免的是**「整卡名入正文」这个不成立的期待**，不是卡片本身。

**判定口径的局限（须知道）**：`元设定` 是**人工打的标签**，不是自动推断。
新卡片默认是「世界里有什么」，只有明确约束「怎么写」时才打此标签——
否则会变成「报错了就打个标签绕过去」的自欺。

## 6. 一句话

**规范约束行为，IP 库补外部知识，资产库记应然、记忆库记实然，两者互为校验；创作层目前是空的。**
