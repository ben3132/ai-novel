# L3 创作层实现方案

> **问题**：`docs/architecture.md` §5 指出——整条管线唯一的空洞是 L3 创作层。
> 名义上它要干三件事：**拆书、编写、去AI**；现状是「编写」与「去AI」没有项目承接。
>
> **本文回答**：这一层该做什么、**不该做什么**（不该做的部分是重点），以及怎么落地。
>
> **v2 修订（2026-09-16）**：核对三个现有项目的**真实能力**后，剔除了五项重复实现的设计，
> 并把错误的接口假设纠正过来。修订说明见 §7。

---

## 1. 边界：谁已经在做什么

设计方案前先把边界钉死。**已有项目负责的事，L3 一律不做**——重复实现不只是浪费，
它会让同一份事实有两个写入者，那正是 `architecture.md` 反复强调要避免的。

| 能力 | 归属 | 依据 |
|---|---|---|
| 已写正文的梳理（章节/角色/事件/剧情线结构化提取） | **nms** | `etl.py` + 5 张表；`get_chapter_context` / `query_character` / `search_memory` / `validate_consistency` |
| 位置/世界观/原作知识的归纳与考据 | **xs** | 采集→切片→建窗→建库→向量索引全链；`search_evidence` / `search_hybrid` / `get_entity` / `list_works` |
| 原作角色的判定 | **xs**（经 nah 的 `orphan` 中转） | `workspace.json` 的 `ip_evidence` → `context_windows` 命中即原作角色 |
| 本书设定（应然）的登记与审计 | **nah** | 卡片 + `add`/`brief`/`check`/`orphan`/`sync` |
| **编排时序**（谁先谁后、什么时机调谁） | **L3** ← 唯一没人做 | — |
| **判据裁决**（总纲禁则/铁律/四层判定的可执行化） | **L3** ← 唯一没人做 | 总纲 §23–§25 目前是纯文档 |
| **评审报告**（依据 → 命中 → 建议，可回查） | **L3** ← 唯一没人做 | — |

**关键结论：L3 不建数据库、不存事实、不做检索。** 它是一层**适配 + 判据**，
所有数据都从外部命令取，唯一自有的产出是**评审报告**。

## 2. 剔除项：原方案里重复实现的五处

这一节是 v2 的核心。每一处都是「原方案设计了，但已有项目在做」。

| # | 原方案的设计 | 为什么剔除 | 改为 |
|---|---|---|---|
| ① | **Brief 里自建四块拼装 + Token 预算裁剪** | 拼装本身没问题，但「拉原作事实」这块不该自己实现——xs 已有 `search_hybrid`（混合 RAG + RRF 融合）、`get_entity`（实体证据）、`list_works`（作品清单），全部有跨进程 JSON 入口 | **调用 xs**，L3 只决定「何时调、取几块、怎么拼」 |
| ② | **拉 `nms` 的 `characters`/`world_settings` 做三方对账（原 P4）** | 这是**再实现一遍 nms 的 `validate_consistency`**，而 nms 已实现且覆盖更全（空摘要/孤儿事件/悬挂引用/时间线矛盾） | **调用 `nms validate_consistency`**，L3 只负责把结果与 `nah check` 并列成一份报告 |
| ③ | **自建状态机**（`state/write_state.json` 记录 draft/review/commit 三态） | 状态机是为「可恢复长流程」服务的，而 nms 的 ETL 已有完整的幂等预检 + 断点续传 + savepoint + 重试上限。L3 的流程是**章级短事务**（一章一次 brief→review），没有跨章状态 | **删掉**。L3 只做单章原子操作，失败重跑即可，不需要状态机 |
| ④ | **自建 `rules/lexicon.py` 词表**（小破表/黄静/唐雅…） | 用词铁律已经写在 `nah` 卡片里（如 `小破表` 卡的「正文一律写小破表」、`黄静` 卡的「一律用黄静」），`nah check` 已经审计这类问题。再维护一份词表就有**两个真相源** | **读卡片**，不另立词表 |
| ⑤ | **自建 `reports/` 与 `state/` 目录体系** | `state/` 随 ③ 删掉；`reports/` 保留但降级为**纯派生输出**——删掉可重跑重建，不是数据 | 保留 `reports/`，明确它可删 |

**剔除后 L3 的代码量估算是原来的 1/3**：没有存储层、没有状态机、没有词表、没有 schema 定义。

## 3. 纠正项：两处错误的接口假设

v1 有两处把「`nah` 的实现局限」当成了「整个管线的能力」，写错了。

### 3.1 xs 不是「只能全文 LIKE」

v1 写「④ IP 原作事实 = xs 证据库全文 `LIKE`」。这是从 `nah/orphan.py` 的实现反推的
——`orphan` 确实只用 `context_windows.text LIKE '%名字%'`，因为它的定位就是个零依赖的轻量过滤器。

但 xs 本体有完整检索层（`docs/agent_query_api.md`）：

| 操作 | 用途 | 特征 |
|---|---|---|
| `search_evidence` | 自然语言问题检索 | 返回带作品/章节/窗口/来源/可信等级的原文 |
| `search_hybrid` | 混合召回 | 词法 + 向量，**RRF 融合**，返回 `lexical_rank`/`vector_rank`/`fusion_score` |
| `get_entity` | 某实体的原文提及 | **不自动归纳实体档案**（只在原文层） |
| `list_works` | 列出作品与章节数 | — |
| `get_corpus_status` | 语料统计 | 只把 `source_artifact_count` 称为信源数量 |

**调用方式**（跨进程，不 import）：
```powershell
'{"operation":"search_hybrid","question":"卡洛夫的体型描述","works":["pacific_rim"],"top_k":8}' `
  | python run_ip_agent.py --request-json - --pretty
```

**L3 该怎么用**：只在 Brief 的「原作事实」块调用，且**必须带上 `answer_status` 的语义**——
xs 明确返回 `answer_status: evidence_only`（是候选证据，不是已确认设定）。
所以 Brief 里必须标明这一块是**证据候选**，不能与 `nah` 卡片的**作者裁定**混为一谈。

**还有一条硬约束**：`trust_level=11`（第三方转录）会产生强制警告，正式考据必须与 L1 原件交叉验证。
Brief 里引用 xs 结果时，**必须保留 `trust_level`**，让写的人知道自己看的是几级证据。

### 3.2 「编写」确实是 L3 的活，xs 不做

v1 的疑虑是「xs 会不会已经有生成能力」。核对结果：**没有**。

它的 `get_agent_guidance()` 里 `not_implemented` 明确列了七项——
`automatic_web_source_discovery`、`automatic_work_tree_discovery`、`single_command_end_to_end_pipeline`、
`coverage_report_operation`、`autonomous_research_loop`、`pdf_page_ocr_fallback`、`structured_xml_fdx_extraction`。
而且 `embedded_llm_required: False`、`decision_owner: connected_agent`
——它是个**只读证据工具**，所有判断交回 Agent。

所以「编写」和「去AI」都还是 L3 的活，**但「编写」的实现路径变了**：
不自己接 LLM，而是**把 Brief 交给 Agent**（本会话就是 Agent），L3 只管
「什么时候该给、给什么、拿到结果后校什么」。

## 4. L3 的最终形态

```
                 ┌────────────────────────────────────────┐
   L0 总纲 V2.0 ─▶│ 判据源：§23 一级禁则 / §24 铁律 / §25 四层判定 │
                 └────────────────────────────────────────┘
                                  │ L3 把判据变成可执行检查
                                  ▼
   ┌───────────────┐   ┌──────────────────────────────┐
   │ nah  │ nms │ xs│──▶│           L3                 │
   │应然  │实然 │L1 │只读│                              │
   └───────────────┘   │  brief  → 拼装上下文            │
                       │  review → 判据裁决 + 出报告      │
                       │  commit → 落正文 + 触发审计      │
                       └──────────────────────────────┘
                                  │ 写（唯一出口）
                                  ▼
                       L4  processed/raw/ep_NNN.md
```

**三个动作，各一行说明它调谁：**

| 动作 | 它做什么 | 它调谁 |
|---|---|---|
| `ce brief <名字…>` | 拼装本章上下文（规则 + 应然卡 + 实然前情 + 原作证据） | `nah brief` / `nms get_chapter_context` / `xs search_hybrid` |
| `ce review <章.md>` | 判据裁决，出报告 | 无外部依赖（判据内置）；设定层结果复用 `nah check` |
| `ce commit <章.md>` | 写正文 + 触发审计 | 写 L4；调 `nah check`、`nms validate_consistency` 出报告 |

**边界铁律**（继承 v1，仍然成立）：
- L3 对 `nah`/`nms`/`xs` **只有读权限**。
- `nah check` 报出「正文出现但未登记」时，**L3 不自动 `add`** —— 那是给人看的待办，
  由人决定 `add` 还是改正文。自动 `add` 会让「应然」被「实然」污染。

## 5. `review`：唯一真正原创的部分

三个动作里，`brief` 和 `commit` 是**接线**，`review` 才是 L3 存在的理由。

总纲 §23（8 条一级禁则）+ §24（写作铁律）+ §25（章节四层判定）写得很好，
但**是文档，没人执行**。这是「去AI」空洞的实质。

**做法：把判据变成可回查的三段式报告**，不是打分。

| 闸门 | 判据 | 手段 | 输出 |
|---|---|---|---|
| 禁则闸 | §23 八条 | 模式匹配（"不是A——是B"句式、结尾喊口号、关键词代替画面、原主/穿越者混淆） | 命中位置 + 原文片段 |
| 铁律闸 | §24 | 段落级启发式（一段一意、环境描写是否有戏剧作用、信息是否前置） | 逐条列出可疑段 |
| 设定闸 | `nah` 卡片 + `nms` | **调 `nah check` 与 `nms validate_consistency`** | 转述两者结果，不重算 |

**每条命中必须给三段**：`依据（总纲第几条）` → `命中（原文片段+位置）` → `建议（怎么改）`。
理由：`orphan` 的定位是「人工复核清单，非拦截器」——它的句式启发式精度高、召回有限。
去AI 判定比 orphan **更主观**，所以更不可能是硬闸门。
给「依据→命中→建议」能让人 30 秒内判真假阳性；给一个分数只会让人不知道该怎么办。

**已知局限（必须写在报告抬头）**：禁则闸与铁律闸是**启发式**，精度高、召回有限。
报告是**线索**，不是结论。

## 6. 落地：不分 P0–P4，只分两步

原方案分了 P0–P4 五个阶段。剔除重复实现后，工作量大幅缩减，重排为两步：

| 步 | 做什么 | 为什么是这个顺序 |
|---|---|---|
| **第一步 · `review`** | 输入一章 `.md`，跑三闸门，出报告 | **只读，零风险**；立刻能给已有 89 章出体检报告；先把判据校准好，再让生成流程去面对它 |
| **第二步 · `brief` + `commit`** | 拼装上下文 + 落正文并触发审计 | 有了校准过的判据，才敢自动化写入 |

原先的 P2（`--mock` 双路径）**删掉**——它是为了在无 LLM 环境验收「生成」而设计的，
而 v2 已确认 L3 **自己不接 LLM**（生成交给 Agent），所以 `--mock` 没有存在意义。
原先的 P3（skill 外壳）**并入第二步**——skill 是让 Agent 遵守工作流的外壳，不是独立阶段。
原先的 P4（三方对账）**改成第二步的一部分**——因为不再自建对账逻辑，只是转述
`nms validate_consistency` 的结果。

**项目形态**：独立项目 `novel-creation-engine`（与 `architecture.md` §5 的建议一致）。
零第三方依赖也能跑，照抄 `nah` 的零安装做派。
与外部项目的**全部接口走子进程调 CLI**，不 import——三者的存储形态完全不同
（`nah` 是 md+sqlite，`nms` 是 pg+pgvector，`xs` 是 sqlite+向量索引），
用 CLI 当契约才能各自独立演进。

## 7. v2 修订说明

| 修订 | 内容 |
|---|---|
| **剔除** | Brief 自建检索 → 改调 `xs search_hybrid`；三方对账自建 → 改调 `nms validate_consistency`；状态机整个删掉；词表整个删掉；`--mock` 双路径删掉 |
| **纠正** | xs 不是「只能全文 LIKE」，它有完整检索层（`search_evidence`/`search_hybrid`/`get_entity`/`list_works`）；「编写」确实归 L3，但实现路径改为「交给 Agent」而非自接 LLM |
| **重排** | P0–P4 五阶段 → 两步；代码量约降为 1/3 |

**修订的判据**：一个能力如果已有项目在做，L3 就只做**接线**，不重复实现。
重复实现的风险不是浪费，而是**同一份事实出现两个写入者**——那正是本项目一直在防的事。

---

## 8. 一句话

**L3 不建库、不存事实、不做检索。它只做三件事：按正确时序调外部命令、把总纲判据变成可执行检查、
产出「依据→命中→建议」三段式的可回查报告。**
