# 设计说明

## 问题：LLM 写小说为什么会「胡编」和「失忆」

不是提示词写得不够狠。模型胡编，通常只有两个原因：**它没读**，或者**它没有可读**。

- 你说「不要编造角色」，模型不知道自己不知道什么，该编还是编；
- 你把设定写在一个几万字的 Markdown 里，模型上下文里没有，它就只能凭记忆猜。

所以解法不是「加一句约束」，而是把**该读什么、什么时候读、读完怎么对**变成机器可执行的步骤。

## 四道防线

| 防线 | 机制 | 命令 |
|---|---|---|
| **存** | 一个事实只在一个文件里定义一处，别处只引用 | 卡片 + `[[名字]]` |
| **读** | 动笔前强制读档，走文件原文而不是模型记忆 | `scan` / `brief` |
| **防漏** | 关系、势力这类最易漏的知识点靠双向标注互锁 | `add --rel` + `check` |
| **校** | 写完必过一致性闸门 | `check` + `sync` |

关键在「读」这一步。`brief` 先把该读的卡片取出来、拼成资料包，模型手里才有据可依 ——
**这是确定性的检索步骤，不是提示词工程。**

## 为什么是 Markdown 卡片，而不是数据库 / 向量库

把三件事分开看：

| 方案 | 擅长 | 在本场景的失效模式 |
|---|---|---|
| **Markdown 卡片** | 人读人改；存储格式＝交付格式，零转换 | 资产上千后人工检索费劲 |
| **SQLite** | 结构化查询、事务、约束 | 作为唯一存储时，人没法直接改，且失去「随手写一段」的便利 |
| **向量库** | 语义相似检索 | 需要的是**身份精确匹配**，近似检索在这里是负资产 |

关于向量库的判断值得展开。本场景的失效模式是「**AI 不知道某个名字已经存在**」，
这要求**身份精确匹配**：

- 卡片措辞和正文不一样 → 向量检索可能**整条漏掉**，AI 反而更没依据地编；
- 返回「相似但不对」的卡 → AI **照着错的写**；
- 漏了还查不出为什么 —— embedding 不可解释。

当全库体量还小（几千字、2–3K token）时，top-k 近似检索带来的不是效率，而是风险。
**全量都装得下的时候，近似就是纯粹的损失。**

向量库真正的主场是另一件事：「我之前写过哪些桥段跟这个情绪像」——那是**借鉴而不抄袭**的需求，
对象是**正文**，不是设定卡。用向量库管设定卡是拿错了工具。

## 为什么还是加了 SQLite

因为有两股力量会让「全库都装得下」这个前提失效：

1. **资产会膨胀** → 需要「找出符合条件的资产」（`find` / `query`）；
2. **旧设定会改** → 需要**变更可追溯** + **改动的影响面传播**。

第 2 条是文件系统和向量库**都给不了**的。所以 SQLite 被加在卡片**之上**，定位是**派生索引**：

- 卡片仍是唯一真相源，写入只走卡片；
- `assets.db` 随时可由 `sync` 一条命令重建；
- `query` 只允许 `SELECT`，从机制上杜绝它变成第二个真相源。

> 这类系统最典型的烂法，就是索引层悄悄变成了第二份真相。这里用「派生 + 只读查询 + 可重建」三条把它锁死。

## 变更处理的三个机制

**① 变更史（`history`）**
`sync` 对比卡片前后状态，把差异 append 进 `revisions` 表。正文变更只记**增删行摘要**，
不把整篇灌进历史。任何一次改动都能回答「谁在何时因何改了什么」。

**② 影响面（`impact`）**
改一个设定前，先反查谁引用了它。**设定类改动无法自动传播**，只能靠这张清单人工复核。

**③ 改名传播（`rename`）** —— 最容易翻车的一步

改名要做三件事，缺一不可：

1. 卡片改名、文件改名；
2. **旧名降级为 `retired` 别名** —— 这样以前几十章正文里的旧写法仍然能被 `scan` 命中，不会失联；
3. 全库 `[[旧]]` → `[[新]]` 自动改写。

只做第 1 步，全库立刻产生一堆断链引用。所以有一条铁律：**改角色名必须走 `rename`，不许手工改文件名。**

配套地，`history` 会沿改名链回溯前身 —— 否则改名前的那段历史就查不到了。

## 引擎与数据分离

早期版本把引擎和数据放在同一个目录（`<小说>/设定资产/`），带来三个问题：

- 项目名靠「上级文件夹名」推断，换个目录就错；
- 正文章节目录写死；
- 一部小说一份工具副本，改一处要同步多份。

现在：**引擎是引擎，工作区是工作区**。工作区只需一张 `workspace.json`
声明「我叫什么、有哪些类型、正文在哪」，其余全部由引擎从命令行参数解析。

```
引擎（本项目）  ──管理──▶  工作区 A（小说甲）
                        ├ 工作区 B（小说乙）
                        └ 工作区 C（小说丙）
```

开新书 = `nah init`，不需要复制代码。

## 一个技术细节：中文全文检索不用 FTS5

SQLite 的 FTS5 默认分词器 `unicode61` 对中文基本无效（会把整句当一个 token），
`trigram` 分词器又要求至少 3 个字符，而中文人名多是 2–3 字 —— 正好卡在边界上。

所以在**中文人名/专名**这种场景下，朴素的子串匹配（`LIKE %词%`）反而更可靠。
真需要全文检索时，数据库层的 `body` 字段本身也还在，可以随时换方案。
