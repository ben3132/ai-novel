# novel-asset-hub

> AI 小说创作的**设定资产管理器**。让 LLM 写到的每个人物、势力、能力、道具、地点，
> **先查库再落笔** —— 不许凭空造新设定，也不许忘掉既有设定。

零第三方依赖，只用 Python 标准库。

---

## 它解决什么

| 痛点 | 后果 | 本工具的机制 |
|---|---|---|
| AI 每次设计情节都**新造角色** | 一本长篇冒出几十个一次性人名 | `add` 三层查重：同名／同别名→硬拦；相似度（含中文逐字重合）→疑似重复 |
| AI **忘了自己之前的设定** | 同一个人前后两个性格、两套关系 | 卡片持久化 + `scan` 命中统计 + `brief` 写前把原文喂回上下文 |
| 大纲/正文里**冒出一个库里没有的名字** | 设定越写越飘，事后无法收敛 | `scan` 报「未登记引用」（单文件）；`orphan` 全库反向扫描（自动区分原作角色） |
| 设定**改过之后前后矛盾** | 改了名，前面 89 章全失联 | `rename` 全库传播 + `history` 变更史 + `impact` 影响面 |
| 资产**膨胀后 grep 找不动** | 想知道「环太平洋线还有哪些待确认资产」无从下手 | SQLite 派生索引：`find` 条件筛选 / `query` 直接跑 SQL |

---

## 两个核心概念

### 1. 卡片是唯一真相源

设定内容全部写在 `<工作区>/cards/<类型>/<名字>.md` 里，人读人改。
`assets.db`、`_registry.json`、`00_索引.md` **全部是派生缓存**，随时可由命令重建 ——
所以永远不会出现「库里和文件里两个说法，AI 随便挑一个」这种烂法。

### 2. 引擎与数据分离

```
novel-asset-hub/          ← 引擎（本项目）：只有代码，不含任何小说数据
     nah/                 · core.py       内容层：卡片读写 / 查重 / 扫描 / 资料包 / 审计
                          · db.py         索引与版本层：SQLite 查询 / 变更史 / 影响面 / 改名
                          · workspace.py  工作区发现、配置与脚手架
                          · cli.py        统一命令行
     tests/               单测（36 项）
     templates/card.md    卡片模板

<任意小说>/设定资产/      ← 工作区（数据）：一部小说一个，可有很多个
     workspace.json       工作区配置（项目名 / 类型集合 / 正文章节目录）
     cards/<类型>/<名字>.md   ★ 唯一真相源
     assets.db            派生：SQLite 索引
     _registry.json       派生：机读索引
     00_索引.md           派生：人读索引
     _log.md              变更日志
```

同一个引擎可以同时管多部小说 —— 开新书不用复制代码，`nah init` 出一个新工作区即可。

## 快速开始

```bash
# 0) 不需要安装。直接跑：
python nah.py --help

# 1) 把某个目录初始化为工作区，并登记一个短名字
python nah.py init "/path/to/新书/设定资产" --name 新书 --as-name 新书 --chapters ../正文

# 2) 登记第一个资产（自动查重）
python nah.py --ws 新书 add --type 人物 --name 李明 --world 主世界 \
    --one-line "主角" --alias 小明 --rel "所属:第七班"

# 3) 动笔前：本章涉及哪些资产？有没有库里没有的名字？
python nah.py --ws 新书 scan ../正文/ep_001.md

# 4) 动笔前：把相关资料原文拉成资料包，读进上下文再写
python nah.py --ws 新书 brief ../正文/ep_001.md --out _资料包.md

# 5) 写完：同步索引与变更史 + 全库审计
python nah.py --ws 新书 sync --note "第一章"
python nah.py --ws 新书 check
```

### 怎么指定工作区（四选一）

```bash
python nah.py --root "/path/to/设定资产" list   # ① 显式路径
python nah.py --ws 新书 list                      # ② 用登记过的名字
set NAH_ROOT=/path/to/设定资产 && python nah.py list   # ③ 环境变量
cd /path/to/设定资产 && python nah.py list      # ④ 直接进目录
```

`--root` / `--ws` 写在子命令前后都行。优先级：`--root` > `NAH_ROOT` > `--ws` > 配置里的默认工作区 > 当前目录。

工作区之间切换：

```bash
python nah.py ws list            # 列出已登记工作区及其状态
python nah.py ws add 我的小说 "/path/to/我的小说/设定资产" --default
python nah.py ws use 我的小说    # 设为默认，之后可不带 --root
python nah.py ws show            # 看当前解析到了哪个工作区
python nah.py ws rm 我的小说     # 解除登记（不动磁盘文件）
```

## 命令总览

### 工作区

| 命令 | 作用 |
|---|---|
| `init <路径>` | 初始化工作区骨架（cards/ + workspace.json + _log.md + README.md） |
| `ws list/add/use/rm/show` | 工作区登记与查看 |

### 内容层（写前 / 写中 / 写后）

| 命令 | 阶段 | 作用 |
|---|---|---|
| `scan <文件>` | **写前** | 命中哪些已登记资产 + 哪些名字库里没有（未登记引用） |
| `brief <文件> [--out F]` | **写前** | 把命中资产的卡片原文拼成「资料包」 |
| `add` | 写中 | 登记新资产，三层查重 |
| `ingest <json>` | 写后 | 批量导入本章新设定 |
| `check [--chapters D]` | 写后 | 六类一致性审计（含**反向扫描**：正文出现但未登记） |
| `orphan [--min-count N]` | 写后 | 全库反向扫描：正文出现但未登记的名称，用 IP 证据库自动区分原作角色 |
| `index` | 维护 | 重建 `_registry.json` / `00_索引.md` |
| `list` / `show` / `log` | — | 列资产 / 看卡片原文 / 记日志 |

### 索引与版本层

| 命令 | 作用 |
|---|---|
| `sync [--note 说明]` | 卡片 → 索引库，并记录本次变更 |
| `find --type/--world/--status/--tag/--grep/--alias` | 条件筛选（对付资产膨胀） |
| `query "<SELECT ...>"` | 直接跑 SQL（**仅 SELECT**） |
| `history <名字>` | 完整变更史（会自动沿改名链回溯前身） |
| `recent [N]` | 全库最近 N 条变更 |
| `impact <名字>` | 改它会牵动谁（反向引用 / 影响面） |
| `rename <旧> <新>` | 改名并全库传播 |
| `dupe` | 别名冲突 |
| `info` | 索引概况 + 新鲜度检查 |

## 强制工作流

**① 动笔前 · 必做**

```bash
nah scan  <大纲或章节>     # 有未登记引用就停下来，先 add 或确认笔误
nah brief <大纲或章节> --out _资料包.md
```
然后把 `_资料包.md` 读进上下文再写。大纲里提到人物/势力/道具，建议写成 `[[名字]]`，工具才能做断链检查。

**② 需要新角色 / 新设定 · 必走 add**

被查重拦下时**默认不许 `--force`**，先判断：是同一人的另一种写法（→ 改既有卡片的 `aliases`），还是真新角色（→ 才 `--force`）。

**③ 写完一章 · 回流 + 审计**

```bash
nah ingest _new_assets.json
nah check        # 六类审计，其中「正文出现但未登记」是双向校验的反方向
```
`check` 报的 **断链引用** 与 **别名冲突** 必须清零；**未登记项**逐条确认（新增则 `add`，笔误则改正文，原作角色则交给 IP 库）。

只要写了正文，`check` 就会顺带做反向扫描。想单独看详细分组（未登记 / 原作已知 / 已登记）用：

```bash
nah orphan
```

**④ 只要动过 cards/ · 收尾必跑 sync**

```bash
nah sync --note "本次改了什么"
nah info        # 卡片比索引新会告警
```

## 卡片格式

```markdown
---
name: 黄静
type: 人物
status: 稳定          # 稳定 / 重判中 / 已变更 / 待确认 / 草稿
aliases: [黄静, 黄精]  # ★关键：简称、错字漂移写法都挂上，否则检索会漏
tags: [主世界]
world: 主世界
first_seen: ep_001
updated: 2026-09-15
---

# 黄静

## 一句话
热血青年，老油条，有故事。

## 档案
- …

## 关系
- 相配：[[王瑶]]

## 写作注意
- 「黄精」是历史漂移写法，正文一律用「黄静」。
```

- 类型默认 7 类：`人物 / 势力 / 能力 / 道具 / 地点 / 设定 / 剧情线`，可在 `workspace.json` 里改成任意集合。
- **跨实体引用一律写 `[[名字]]`** —— 断链检测与双向标注检查都靠它。
- 一个事实**只在一个文件里定义一处**，别处只引用、不复制。

### `tags: [元设定]` 是干什么的

有些卡片约束的是**怎么写**，不是**世界里有什么**——比如「三主体架构」（叙事分工）、
「世界×英雄配置」（作者侧配置表）、「设定修正三规则」（修订台账）。这类卡片的**整卡名
本来就不该出现在正文里**，所以给它们打 `tags: [元设定]`：

- `check` 不再把它们报为「已登记但正文未出现」，改判「**其实例是否落地**」
  （只看 `## 档案` 段里写的实例名，全部落空才提示）；
- 正文里真正对应的是具体说法，如「变身规则」在正文里是 ep_037 的「U 盘」、ep_058 的「倒模」。

⚠️ 这是**人工标签**，不是自动推断：默认所有卡片都是「世界里有什么」，
只有明确约束「怎么写」的才打此标签——否则就成了「报错了打个标签绕过去」。

## 为什么是「Markdown 卡片 + SQLite 派生索引」

**没有用向量库。** 失效模式是「AI 不知道某个名字已经存在」，这需要**身份精确匹配**，而向量检索是近似的：

- 卡片措辞和正文不一样 → 可能整条**漏掉**，AI 反而更没依据地编；
- 返回「相似但不对」的卡 → AI **照着错的写**；
- 漏了还查不出为什么 —— embedding 不可解释。

向量库真正的主场是「我之前写过哪些桥段跟这个情绪像」（借鉴而不抄袭），那对象是**正文**，不是设定卡。

**SQLite 是加在卡片之上的索引层，不是第二个真相源。** 它换来三件文件系统给不了的能力：结构化查询、变更可追溯、反向引用。删掉 `assets.db` 一条 `sync` 就能重建。

> 完整设计论证见 [`docs/design.md`](docs/design.md)。

## 已知边界

- `scan` 只能识别**已登记的名称/别名**与 `[[ ]]` 标记，单文件视角。**全库反向扫描**由 `orphan` 负责。
- `orphan` 是**句式启发式**，不是通用中文 NER：它靠「说话动词锚点 + 介词对象 + 称谓词 + 词频裁剪」抽候选，所以
  - **精度高**（噪声被词频与停用词表挡掉），**召回有限**（作者的句式变了就会漏）；
  - 定位是**人工复核清单**，不是自动拦截器；
  - `--min-count` 调门槛、`--no-ip` 关掉 IP 证据库退回二分类。想让召回更稳，可在写作时于大纲/正文保留 `[[双链]]`（那是精确引用，优先级最高）。
- 卡片是 Markdown，**不校验内容真伪**，只保证结构一致性（谁引用了谁、有没有冲突、有没有遗漏）。内容的正确性以作者裁定为准。
- **`check` 的「正文未出现」有归因歧义**：报出来只说明「这个名字没在正文里逐字出现」，原因可能是
  ①冗余登记 ②别名没挂全 ③整卡名本就不入正文（→ 打 `元设定` 标签）④卡片名与正文用词不一致
  （如「超自然复苏」vs 正文「灵气复苏」，→ 在 `aliases` 挂上正文用词）。**四类都得人判**。
- 中文全文检索用朴素的子串匹配而**不是 FTS5**：FTS5 默认的 unicode61 分词对中文无效，trigram 分词又要求至少 3 字，而中文人名多是 2–3 字。

> 这套工具在整条创作管线里的位置、与 IP 采集项目 / 记忆系统的分工，见 [`docs/architecture.md`](docs/architecture.md)；
> 下游「创作层」怎么补（编写 / 去AI），见 [`docs/creation-layer.md`](docs/creation-layer.md)。
